# PostgreSQL arm: porting notes

Written 2026-08-12 while the MySQL campaigns were still running, which is why the
port arrived as new files only. Nothing the in-flight campaign reads was touched.

## What exists

| MySQL arm | PostgreSQL arm | Notes |
|---|---|---|
| `docker-compose.yml` | `docker-compose.pg.yml` | Same cpuset layout (db 0,1 / app 2,3 / k6 4,5), same memory limits. Separate file so the two stacks cannot interfere; they must not run measurements concurrently. |
| `db/schema.sql` | `db/schema-pg.sql` | Identical tables and index set. `AUTO_INCREMENT` becomes `GENERATED BY DEFAULT AS IDENTITY` so the seeder can insert explicit ids. |
| `db/my.cnf` | `db/postgresql.conf` | Intent-mapped, one comment block per setting. Buffer pool -> shared_buffers 3GB; stats_auto_recalc=0 -> autovacuum off; AHI off -> jit off; skip-log-bin -> wal_level minimal. |
| `db/seed.sh` | `db/seed-pg.sh` | Same scales, chunking, hot tier, validation gates. `generate_series` replaces the recursive CTE. |
| `scripts/set-netem.sh` | `scripts/pg/set-netem-pg.sh` | Same sidecar pattern (`network_mode: service:postgres`). |
| `scripts/warmup.sh` | `scripts/pg/warmup-pg.sh` | InnoDB buffer-pool dump/load becomes `pg_prewarm()` per relation (already deterministic, no polling). Warm gate reads `pg_statio_user_tables` deltas. Filesort check becomes a Sort-node check. |
| `scripts/calibrate.sh` | (reused as is) | Engine-agnostic: probes the app's `/calibrate` endpoints. Point `APP_URL` at `http://localhost:18081`. |
| `k6/` | (reused as is) | k6 talks HTTP to the app; `BASE_URL` in the pg compose file targets `lab-app-pg`. |
| `app/` | (same image) | All queries are JPQL; no native SQL anywhere. The only change is the PostgreSQL JDBC driver in `build.gradle`. Hibernate picks the dialect from the URL. |

## Cross-engine dataset identity

With `SEED` set, both seeders derive every random draw as
`md5(seed || ':column-salt:' || row_number)` first-8-hex-digits scaled to [0,1].
MD5 of the same string is the same on both engines, so a seeded PG run holds the
same rows as a seeded MySQL run: same policy assignments, member assignments,
statuses. Only wall-clock-derived timestamps differ, exactly as between two
seeded MySQL runs. `seed-pg.sh` asserts the `bit(32)::bigint` cast semantics and
the determinism of the rendered expression at runtime before seeding.

Two parity-preserved quirks, reproduced deliberately rather than fixed, because
the MySQL dataset the paper measured has them:

1. A draw of exactly `ffffffff` maps member_id to `MEMBER_COUNT + 1`, which is a
   dangling reference (probability ~2^-32 per draw; same on both engines).
2. The hot tier's rnd stream re-uses row numbers 1..HOT_TOTAL, so hot-tier rows
   share draw values with the first uniform-tier rows for the same column salts.
   This correlates the two tiers' status/policy columns; it does not affect
   engine parity.

## What the PG arm is for

The paper's IN-list boundary is `eq_range_index_dive_limit = 200`, a MySQL
planner constant. PostgreSQL has no dive limit; its planner estimates from
statistics at any IN-list length. So the PG arm answers: do the N-axis
thresholds and the batch-fetch rescue transfer to an engine without that
constant? Either answer is a result: transfer strengthens generality, and
divergence localises the MySQL finding to its planner mechanism.

## Not done yet (deliberately)

- `run-cell.sh` / `run-campaign.sh` are MySQL-arm-only until the current
  measurement queue drains; they will gain an `ENGINE` switch afterwards rather
  than being forked. Nothing here blocks that: every primitive the runner needs
  (netem, warmup, seed, compose stack) exists on the PG side already.
- The app image needs one rebuild (`docker-compose -f docker-compose.pg.yml
  build app-pg`) to pick up the PostgreSQL driver; not done while the MySQL
  campaign holds the host.
- Cell selection for the PG campaign (which subset of the MySQL grid to
  replicate) is an analysis decision, recorded separately once stage 2/3/4
  results are in.
